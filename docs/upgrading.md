# Sari-IMS: Upgrading & Rollback Guide

This guide details how to update an active Sari-IMS deployment to new versions with automated safety backups and zero data loss.

---

## 1. Automated Upgrade Procedure

Sari-IMS includes an upgrade script (`deploy/update.sh`) that automates the upgrade workflow:

```bash
cd deploy
./update.sh
```

### The 6-Step Automated Update Sequence:
1. **Automated Safety Backup**: Executes `deploy/backup.sh`, creating a compressed PostgreSQL dump in `deploy/backups/`.
2. **Pull Images**: Pulls updated container images from GHCR without altering persistent volumes.
3. **Recreate Containers**: Performs `docker compose up -d --remove-orphans`.
4. **Health Verification**: Waits for PostgreSQL and Redis readiness probes.
5. **Schema Migrations**: Runs `php artisan migrate --force` to apply any database schema changes.
6. **Liveness Validation**: Queries `/health` and `/health/ready` to verify service functionality.

---

## 2. Upgrading to a Specific Version Tag

By default, `deploy/.env` specifies `TAG=latest`. To pin your deployment to a specific release version (e.g. `v1.1.0`):

1. Edit `deploy/.env`:
   ```env
   TAG=v1.1.0
   ```
2. Execute `./update.sh`.

---

## 3. Deterministic Rollback Procedure

If an issue occurs after an upgrade, you can roll back to the previous known good release:

### Step 1: Revert Image Tag
Edit `deploy/.env` to point to the prior version tag:
```env
TAG=v1.0.0
```

### Step 2: Restart Containers
```bash
docker compose up -d --remove-orphans
```

### Step 3: Restore Pre-Update Database Snapshot (If Required)
If the new version executed irreversible schema migrations, restore the pre-update backup:
```bash
# Locate the backup generated by update.sh in deploy/backups/
LATEST_BACKUP=$(ls -t backups/sari_backup_*.sql.gz | head -n1)

# Restore database
gunzip -c "${LATEST_BACKUP}" | docker exec -i sari_postgres_prod psql -U sari_prod_user -d sari_inventory
```

### Step 4: Verify Health
```bash
curl -s http://localhost/health/ready
```
